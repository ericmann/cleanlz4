# Spike P2-09: the oracle's frame behaviour

## Question

What does `oracle::frame::decompress_frames` return for each frame-level probe,
and where does it differ from the verdicts the plan fixes for cleanlz4?

## Method

`cargo run -p oracle --bin probe_frame` builds each probe with
`oracle::craft_frame` (a frame laid out as the Frame format describes, with
overrides for any field) and decodes it with the oracle and with cleanlz4. The
oracle's decoder is called once per frame with a fresh context, looping over
the input (`oracle::frame::decompress_frames`). The table below is the binary's
output, unedited. "cleanlz4 fixed" is the verdict the plan fixes; "cleanlz4
actual" is what the decoder did when this spike ran.

## Probes where the oracle differs from cleanlz4's fixed verdict

| probe | oracle | cleanlz4 fixed | normalization |
|---|---|---|---|
| legacy frame, with and without a zero terminator | reject (unknown frame type) | accept | `legacy-frame` |
| Dict-ID and no dictionary | accept | reject | none: the comparison retries cleanlz4 with an empty dictionary when it reports `DictionaryRequired`, and the retried result is compared |

Every other probe agrees in accept or reject. Both sides reject the trailing
garbage probes (one, three and eight bytes), the content-size probes (too small
and too large), the block size probes, the reserved bits, wrong versions,
invalid block maximum sizes and every bad checksum, and both accept the empty
input, a skippable frame alone, a skippable frame before a regular one and a
zero-size uncompressed block.

Note on the Dict-ID row: cleanlz4's "actual" column shows an accept because the
dictionary task (P2-08) was skipped when this spike ran, so cleanlz4 does not
yet report `DictionaryRequired`. The comparison module already carries the
retry, and `crates/oracle/tests/diff.rs` exercises it with an injected decoder.

## Normalizations

| id | what | justification |
|---|---|---|
| `legacy-frame` | cleanlz4 accepted and `FrameOutput.kinds` contains `Legacy`, the oracle rejected | The oracle's frame decoder does not know the legacy magic number; the document defines the legacy frame (Frame format, "Legacy frame"), so cleanlz4 decodes it. |
| `zero-offset` | cleanlz4 rejected with `ZeroOffset`, the oracle accepted | Found in P1-07: the document calls a zero offset invalid (Block format, "Compressed block format": "denotes an invalid (corrupted) block"); the oracle tolerates it. |

No normalization exists for content size or skippable frames: the oracle
agreed with cleanlz4's fixed verdicts on both.
